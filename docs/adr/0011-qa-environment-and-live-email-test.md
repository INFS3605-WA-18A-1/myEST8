# A QA environment on the home server, and a live email test

CI proves the code with every external API mocked, so nothing proves that a real email makes the round trip: Gmail to Resend inbound, through the signed webhook and the tunnel, into a Maintenance Request, and back out through Resend to the Tenant's inbox. This adds a **QA environment** and a **journey test** that sends real email through it. [Hosting](../hosting.md) and [ADR 0006](0006-resend-email-and-claude-haiku.md) describe the live pieces it copies.

**Where.** QA runs on the home server, next to the live app, deployed from a `qa` branch (`git push origin dev:qa` before a release). The server is where the Cloudflare Tunnel, the local Postgres and the live secrets already are, and it costs nothing. Vercel and Supabase have no free second environment: the one Supabase project is production ([vercel.md](../vercel.md)), and a preview would run on its data. A GitHub Actions runner on the same server (a self-hosted runner labelled `home-qa`) deploys and tests it, so the secrets never leave the machine.

**Its own database.** QA keeps its data in the local Postgres from `scripts/db.ts`, in the schema `qa`, beside `live`, never in the production Supabase. `serve.sh` only accepts the schemas `live` and `qa`, `deploy/qa-exec.sh` strips any hosted database or storage address from the environment before loading QA's settings, and QA's seed and migrations refuse a Postgres that isn't on this machine. Files stay in the database (QA never sets `SUPABASE_URL`). The journey creates and rejects a Maintenance Request on every run; that must never reach real Agencies' data.

**Its own secrets.** `~/.config/myest8/qa.env` (outside the repository, `deploy/qa.env.example` is the template) holds QA's own Resend key, webhook secret and inbound domain, its test Gmail account's OAuth client and refresh token, and the Property Manager's password. It shares none of them with `live.env`: a leak or a quota spent in QA can't take production down, and a bug in a QA script can't send as the live Agency. `DEMO_SEND_TO` is set to the test Gmail address, so QA may really email that one address and no other; anything else goes to the phone simulator only.

**Its own Resend account.** Checked on 2026-10-21 ([pricing](https://resend.com/pricing), [quotas and limits](https://resend.com/docs/knowledge-base/account-quotas-and-limits)): the Free plan includes inbound receiving, 3 domains, **1 webhook endpoint**, 100 emails a day (a UTC day) and 3,000 a month, and a received email counts against the quota like a sent one. A second team in the same account needs a paid plan ([Multiple Teams](https://resend.com/blog/multiple-teams)). So QA can use its own subdomain (it would fit in the 3 domains) but can't share production's Resend team: the team has one webhook endpoint, which production uses, and QA's runs would spend production's 100 a day. QA therefore uses a **second free Resend account** (signed up with the test Gmail address) with its own inbound subdomain, such as `qa-mail.<domain>`. One journey is about 12 emails (the report and four answers in, the acknowledgement, four questions, the photo link and the rejection out), so a nightly run and a handful of manual ones stay far under 100 a day. Whether Resend's terms are happy with two free accounts held by one person isn't something its pages say; if it matters, the fallback is paying for QA's team, or running the journey less often.

**Why nightly and by hand, not on pull requests.** The journey sends real email, spends Resend's daily quota and Claude's tokens, depends on three outside services answering within minutes, and takes several minutes. On every pull request it would burn the quota, fail for reasons that are not in the change, and need the test Gmail credentials in a workflow that runs fork code. It runs on a push to `qa` (a release candidate), nightly, and from the Actions tab. The repository is public, so the workflow has no `pull_request` trigger: a self-hosted runner must not run code from forks. The journey also never runs twice at once (one concurrency group), and a run is never cancelled mid-send.

**What it does.** As the Tenant (the test Gmail account), it emails a routine dripping-tap report to the QA Agency's inbound address with a unique token, then: checks the acknowledgement arrives in the Gmail inbox from the Agency's address and says the right thing; answers the four guided questions by email; opens the photo link and uploads a photo; signs in to the QA app as the Property Manager and finds the Maintenance Request by its token; then rejects it (the app emails the Tenant) and trashes the run's messages. Every wait polls with a deadline. It refuses to start if a variable is missing, if `PUBLIC_URL` is the production address or isn't a `qa-` hostname, or if the inbound address is on production's domain. `scripts/qa-seed.ts` makes the QA Agency and Property Manager idempotently through the app's own sign-up code, so there is nothing to click.

**What it proves.** The tunnel and DNS route to the QA app; the Resend inbound MX, webhook signature and body fetch work; an email from a real mail server is matched to a Tenant and Property and runs the guided flow; outbound email through Resend authenticates and reaches Gmail's inbox, not its Spam folder; the app's side (sign-in, upload link, the Maintenance Request page, rejection) works on a real database; and the Gmail credentials still work (a lapsed token fails the run, which is the point).

**What it doesn't.** It isn't production: Vercel, Supabase Storage, the Supabase database and the production secrets, domain and Resend account are not exercised, so a mistake in them still needs the release's own `smoke` job. It doesn't test other channels (SMS, WhatsApp), photos judged by a vision model, quotes, Tradie or Property Owner emails, or the schedule and visit flows. Claude's reading of the email is covered only when `ANTHROPIC_API_KEY` is set in `qa.env`; without it QA uses the free in-process classifier. It sends one kind of report, so it can't say the classifier is right in general. It runs only as often as QA does: a regression after the nightly run is found the next night.

**Costs and risks.**

- The test account's refresh token lapses after 7 days while the OAuth consent screen is in Testing, or at any time on a password change or revoked access, and after six months unused ([Google's OAuth documentation](https://developers.google.com/identity/protocols/oauth2#expiration), updated 2026-10-16). `docs/qa.md` has the account's consent screen published ("In production", still unverified, which is allowed for one's own account) so the token doesn't lapse; a lapse makes the run fail with that message.
- The Gmail permission is `gmail.modify` (read, send and trash; no permanent delete, no settings), because the journey tidies its own mail. It is a restricted scope, and the token only opens the throwaway test account.
- A self-hosted runner executes whatever its workflow says, on the home server. Only a push to `qa` (which needs write access), a nightly schedule and a manual run start it, and `docs/qa.md` has the repository require approval for workflows from outside collaborators, so that a pull request from a fork can't name the `home-qa` label and run on the server.
- The journey's log is uploaded as an artifact on failure, and a public repository's artifacts can be downloaded by anyone. The log therefore masks every secret, the test account's address, the Property Manager's address and the Tenant's upload link.
